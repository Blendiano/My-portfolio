# Code Style

## 1. General Principle

Write code that is:

- Clear
- Simple
- Readable
- Consistent
- Maintainable
- Easy for another developer or AI agent to understand

Prefer readability over cleverness.

---

## 2. HTML

Use semantic HTML.

Prefer:

```html
<header>
<nav>
<main>
<section>
<article>
<footer>
<button>
```

instead of unnecessary `<div>` elements.

Use headings in logical order:

```text
h1
 ├── h2
 │    ├── h3
 │    └── h3
 └── h2
```

Do not skip heading levels simply for visual styling.

---

## 3. HTML Naming

Use descriptive class names.

Preferred:

```html
<section class="projects-section">
<div class="project-card">
<h2 class="section-title">
```

Avoid:

```html
<div class="box1">
<div class="thing">
<div class="blue">
```

Classes should describe purpose, not appearance.

---

## 4. Accessibility

Every meaningful image should have useful alt text.

Decorative images should use:

```html
alt=""
```

Interactive elements must be keyboard accessible.

Do not create clickable `<div>` elements when a `<button>` or `<a>` is appropriate.

---

## 5. CSS Naming

Use readable kebab-case:

- `.project-card`
- `.project-card__title`
- `.project-card__description`

BEM-style naming may be used when it improves clarity.

Do not mix multiple naming systems randomly.

---

## 6. CSS Variables

Design tokens must use CSS custom properties.

Example:

```css
:root {
  --sys-primary: hsl(221, 83%, 53%);
  --sys-background: hsl(60, 14%, 97%);
  --sys-text: hsl(0, 0%, 9%);
}
```

Use the `--sys-*` roles generated by `Tokens/build-css.js` (see `design-system.md`).

Use tokens throughout the project.

Avoid repeated magic values.

---

## 7. CSS Organization

Organize CSS roughly in this order:

1. Design tokens
2. Reset/base
3. Typography
4. Layout
5. Components
6. Sections
7. Utilities
8. Responsive rules

---

## 8. Responsive CSS

Use mobile-first CSS where practical.

Example:

```css
.project-grid {
  display: grid;
  grid-template-columns: 1fr;
}

@media (min-width: 768px) {
  .project-grid {
    grid-template-columns: repeat(2, 1fr);
  }
}
```

Avoid excessive breakpoint definitions.

---

## 9. JavaScript Naming

Use camelCase:

- `projectCard`
- `initializeNavigation`
- `mobileMenuButton`

Functions should use verbs:

- `initializeNavigation()`
- `renderProjects()`
- `validateForm()`
- `toggleMenu()`

---

## 10. Constants

Use `const` by default.

Use `let` only when reassignment is required.

Avoid `var`.

---

## 11. Functions

Functions should generally have one clear responsibility.

Bad:

```javascript
function doEverything() {}
```

Prefer:

```javascript
function renderProjects() {}
function filterProjects() {}
function initializeProjectFilters() {}
```

---

## 12. DOM Queries

Cache frequently used DOM elements.

Example:

```javascript
const menuButton = document.querySelector(".menu-button");
const mobileMenu = document.querySelector(".mobile-menu");
```

Check that elements exist before operating on them when the script can run across multiple pages.

---

## 13. Error Handling

Use defensive checks.

Example:

```javascript
if (!menuButton || !mobileMenu) {
  return;
}
```

Do not allow missing optional elements to break the entire page.

---

## 14. Comments

Comments should explain:

- Why something exists
- Why a non-obvious decision was made
- Important constraints

Avoid comments that simply restate the code.

Bad:

```javascript
// Set menu open to true
menuOpen = true;
```

Better:

```javascript
// Keep the menu state synchronized with the accessibility attribute.
```

---

## 15. JavaScript Modules

Use ES modules where practical:

```html
<script type="module" src="js/main.js"></script>
```

Separate unrelated functionality into modules.

---

## 16. Strings

Use template literals when interpolation is required.

Example:

```javascript
const title = `${project.title} Case Study`;
```

---

## 17. Data

Keep content separate from rendering logic where practical.

Do not hard-code the same project information in multiple locations.

Prefer `data/projects.js` for structured project information.

---

## 18. No Unnecessary Dependencies

Before adding a library, ask:

- Is it required by the PRD?
- Can native HTML solve it?
- Can CSS solve it?
- Can a small JavaScript function solve it?
- Does the dependency provide meaningful long-term value?

If the answer is no, do not add it.

---

## 19. Formatting

Use consistent:

- Indentation
- Quotes
- Semicolons
- Braces
- Line breaks

Prefer readable formatting over compressed code.

---

## 20. Code Quality Rule

The AI agent must not generate unnecessarily complicated code simply because it can.

The portfolio is a real professional product.

Every line of code should have a reason to exist.
